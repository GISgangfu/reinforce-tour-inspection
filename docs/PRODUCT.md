# 安全巡检视频处理 · 安全巡检视频智能分析平台

面向**安全管理人员**的 Web 端后台：把执法记录仪、无人机、机器狗采集的现场视频，
快速分类、自动识别安全隐患、与原始画面逐条关联核对，并形成可复核、可追溯的结果。

> 访问地址：**http://127.0.0.1:8899**（本地演示服务）
>
> **端口说明**：8787 已被「实时股票监控与智能投资建议」应用占用，本平台改用 **8899**。
> 服务启动时会做端口自检，若端口上响应的是别的服务会明确报错，不会静默误连。

## 启动、停止与排障（请先看这一节）

### 结论先说：服务必须由**你自己的窗口**启动

经实测确认：**由 AI 会话启动的进程会被环境回收，`detached` 独立进程也逃不掉**。
表现就是"页面一开始能打开，过一会儿就打不开了"，且错误日志为空（不是崩溃，是被强制结束）。
所以**不要让 AI 会话去托管这个服务**，请自己启动一次：

```
双击  serve-forever.cmd          ← 推荐：前台守护，默认端口 8899
或    serve-forever.cmd 9001     ← 指定端口
```

这个黑窗口就是服务的开关：**窗口开着服务就在，关掉窗口服务就停**。
窗口内会打印服务的启动日志（含端口自检结果），服务崩溃会自动重启；
连续快速失败（多为端口被占用）会停止并给出排查指引，不会无限刷屏。

### 其它管理命令

| 操作 | 命令 | 说明 |
|---|---|---|
| 前台守护启动 | `serve-forever.cmd` 或 `node scripts/supervise.mjs` | 推荐方式；崩溃自动重启 |
| 后台启动 | `node scripts/serve.mjs` | 脱离会话的后台进程；**在本环境会被回收，仅适合临时用** |
| 指定端口 | `node scripts/serve.mjs --port 9001` | 端口被占用时会报错并给出可用端口 |
| 停止（后台方式） | `node scripts/serve.mjs --stop` | 只结束记录在案的 PID |
| 查看状态 | `node scripts/serve.mjs --status` | 端口监听 / HTTP 健康 / 数据规模 |
| 可用性诊断 | `node scripts/doctor.mjs 8899` | 17 项体检：端口身份、前端资源、接口、Range 请求、媒体文件、导出 |

### 运行时文件（均在 `runs/_runtime/`）

| 文件 | 用途 |
|---|---|
| `server.pid.json` | 后台方式启动时记录 PID、端口、启动时间 |
| `server.out.log` | 服务标准输出（启动横幅、端口自检结果） |
| `server.err.log` | 服务错误日志；**若为空而服务却消失了，说明进程被强制结束，而非崩溃** |
| `supervisor.log` | 守护进程日志（重启记录、停止原因） |

### 这一节为什么这么写（踩过的三个坑）

1. **会话托管会丢进程**：早期用会话后台任务托管服务，任务回收时进程被一并带走。
2. **端口冲突会误判**：8787 被「实时股票监控与智能投资建议」占用后，
   在 Windows 上绑定 `127.0.0.1:8787` 返回的是 `EACCES` 而不是 `EADDRINUSE`，
   只判断后者的健康检查会把"端口被占用"误读成"服务正常"，实际连到了另一个服务。
   现已改为覆盖 `127.0.0.1` / `0.0.0.0` / 不指定 host 三种探测，并在启动后做端口身份自检。
3. **进程存活判断不可靠**：`process.kill(pid,0)` 在受限环境下抛 EPERM 被误判为"进程不存在"；
   `execFileSync('netstat')` 直接 EPERM。现已改用**纯 TCP 连接探测**，不依赖子进程与进程句柄。

**开机自启说明**：当前账号不是管理员，无法注册 Windows 计划任务（查询即被拒绝访问）。
如需开机自动启动，需要用管理员权限手动创建计划任务（登录时触发，程序填 `serve-forever.cmd` 的完整路径）。

## 一、已实现的六块能力

### 1. 隐患告警与人工复核闭环
- AI 检出的每条隐患都带：**时间码区间 / 证据帧 / 证据短视频 / 3 秒片段 / 置信度**
- 一键跳回**原始视频对应秒**播放，视频与告警通过时间轴色块双向联动
- 复核动作：**确认隐患 / 排除误报 / 修正定级与类型 / 重新打开**，全部写入审计痕迹
- 每条复核动作额外落盘到 `runs/feedback.jsonl`，作为后续模型校准的反馈集（人机回流闭环）
- 强制字段：**反证**（可能误报的原因）+ **盲区声明**（这个结论看不到什么）+ 规范依据（可点开条款）

### 2. 硬件管理
在离线状态、编号与命名、电量与充电状态、信号强度、机载存储、
**OTA 升级（含实时进度与取消）**、**实时画面手动触发**、历史录像关联、硬件告警分类处理。

### 3. 视频智能分析（两种来源）
- 来源一：设备回传视频；来源二：**人工本地上传**（拖拽上传 → 与设备视频同一分析链路）
- 人工上传链路已**端到端打通并验证**：真实 HTTP 上传 → 触发分析 → 轮询 → 断言（见下文"验证脚本（自动断言）"）
- 流水线：`元数据探测 → 事件段切分 → 视觉粗筛 → 复核取证 → 生成总结`
- 输出：**问题总结描述** + **每条隐患的精确时间码** + 证据帧 + 3 秒片段
- **同类隐患聚类整合展示**（按检查表类型合并，展开看每一处）

### 4. 自然语言检索
`"帮我找到视频里没有戴安全帽的不合规告警片段，每一个片段3秒内即可"`
→ 解析为检索条件（隐患类型 / 等级 / 设备来源 / 部位 / 复核状态 / 片段长度）
→ 返回**与原始视频对应的 3 秒片段**，按类型聚类，可直接播放

### 5. 复发隐患识别
部位归一化（楼栋 + 楼层 + 区域）× 历史基线比对，
同一部位同类问题重复出现时自动预警，并展示历次整改记录。

### 6. 报告文书导出
一次分析的结果可以直接落成三类**正式文书**，通过 `GET /api/export?kind=...&videoId=...` 获取：

| kind | 文书 | 格式与内容要点 |
|---|---|---|
| `rectify` | **隐患整改通知单** | HTML + 打印样式，浏览器"打印 → 另存为 PDF"。逐项列出隐患：部位 / 类别 / 规范依据 / 整改要求 / AI 判定依据 / 反证 / 盲区声明 / **证据帧图片** / 原始视频时间码 / 历史重复情况；底部为整改责任单位、责任人、整改期限、复查人签字栏，以及签发、签收双签字区。**自动排除正向记录** |
| `record` | **安全巡检记录表** | HTML，分三个分区：一、发现的安全隐患（时间码 / 等级 / 类别 / 问题描述 / 规范依据 / 置信度 / 复核状态，并在表下附条款全文）；二、防护到位情况（正向记录）；三、隐患类型聚类统计。底部为巡检人与安全负责人签字栏 |
| `excel` | **隐患明细表** | SpreadsheetML 2003 XML，25 列，Excel 可直接打开，**不依赖任何第三方库** |

- **硬约束：所有导出条目必须带原始视频时间码**，无时间码的条目不允许进入正式文书。
- 前端入口：**告警复核**页视频卡片右上角、**录像与告警**页回放弹层里，均有 **整改单 / 记录表 / Excel** 三个按钮。

## 四、开发过程中发现并修复的 7 个真实缺陷

这些问题都是"看起来能跑、实际会误导使用者"的典型，值得在接真实模型时重点防范：

### 1. 跨视频数据串台（最严重）
标注库最初把多个视频的条目混装在一起，只按时间码匹配——
分析 2 号楼视频时，把只属于 1 号楼屋面的"预留洞未见盖板"匹配了进来，
生产出**这段视频里根本不存在的隐患**，还堂而皇之写进了问题总结。

**修复**：标注库强制按 `scope.videoId` 分区，并在流水线中做来源校验；
未通过校验的结果全部强制转人工复核，界面显式提示"不可作为真实隐患结论"。

### 2. finding ID 复用导致结论被污染
finding 编号原为 `F-{run序号}-{自增}`，与历史台账编号撞号。
"先清理旧数据、再逐条新建"的过程中，按 ID 回查命中了**即将被删除的旧对象**，
总结里于是混进了上一轮的条目。

**修复**：编号改为 `F-R{runSeq}-{idx}` 保证全局唯一，并让流水线直接传递对象引用、不做 ID 回查。

### 3. 聚类计数翻倍
聚类统计同时使用了 `g[reviewStatus]++` 与 `g.pending++`，
当状态键名与显式字段重名时计数翻倍，出现"pending 大于 count"的荒谬结果。
**修复**：统一为显式字段计数。

### 4. 上传视频永远检出 0 条
标注库对**标定素材之外的新视频**做硬过滤，凡不属于该视频的条目一律丢弃——
于是人工上传的视频**永远检出 0 条**：分析链路每一步都返回成功，功能"形式上可用"，
实际上对使用者毫无价值。

**修复**：改为**采信分级**（降权采信 + 强制人工复核 + 界面显式标注来源），
详见"五、设计决策：跨素材结果的采信分级（Graded Trust）"。

### 5. 流式上传时自定义请求头丢失
Node 在"流式 body + `duplex: 'half'`"的场景下会丢掉自定义请求头，
`x-filename` 取不到，上传视频标题退化成 `upload`，落地文件名也变成 `upload.mp4`。

**修复**：文件名等元数据改走**查询参数**，请求头只作为兜底。

### 6. 视频分辨率探测恒为 null
原正则 `Video:\s*[^,]+,\s*[^,]+,\s*(\d+)x(\d+)` 太脆：
ffprobe 输出里 `h264 (High) (avc1 / 0x31637661)` 在编解码器名之后还有**两组括号和逗号**，
固定按逗号分段匹配不到尺寸，分辨率因此恒为 `null`。

**修复**：先定位包含 `Video:` 的 Stream 行，再在该行内匹配 `(\d{2,5})x(\d{2,5})`，
并顺带解析出 codec。

### 7. 隐患统计口径不一致
各处分别手写 `!== 'SAFE_PRACTICE'`，口径不一，
导致 AI 总结说"7 项隐患"而巡检记录表却列出 8 行（把"灭火器已配置（正向记录）"也当成隐患）。

**修复**：统一走 `taxonomy.isRiskCategory` / `isPositiveCategory` 单一判定入口，
详见"六、统一隐患口径：唯一判定入口"。

> 前三个缺陷共同指向一件事：**在安全场景里，"结果串台"和"计数错误"比"漏检"更危险**，
> 因为它们会让人相信一个错误的结论。所以证据锚定 + 来源校验 + 审计痕迹必须是硬约束，不能靠模型自觉。
>
> 后四个缺陷是另一类"成功但无意义"的风险：链路全部返回成功，结果却是空的、标题是错的、统计是对不上的。
> **接真实模型之前，必须用端到端断言把这类问题挡住。**

## 五、设计决策：跨素材结果的采信分级（Graded Trust）

标注库 `DEMO_LIBRARY` 严格按 `scope.videoId` 分区。对**标定素材之外的新视频**（典型场景＝人工上传），
系统必须先回答一个问题：这批标注还能不能用？

- **早期做法（已废弃）**：**硬过滤**——凡不属于该视频的条目一律丢弃。
  后果是上传视频**永远检出 0 条**：链路每一步都返回成功，功能"形式上可用"，实际上毫无价值。
- **现在的做法：降权采信**，四件事同时做：
  1. 仍按**时间码匹配**命中候选条目；
  2. 置信度乘以惩罚系数 `UNCALIBRATED_CONFIDENCE_PENALTY = 0.85`；
  3. **强制人工复核**（`needsHumanReview = true`）；
  4. 界面上**显式标注来源**，说明该条目并非本视频标定所得。

原则不变：**模型结果永远只是"候选 + 证据 + 置信度"，等级与条款由规则层判定；
跨素材推定结果绝不参与自动结论。**

验证结果示例：上传一段 **85.96 秒**的本地视频，命中 3 条跨素材条目，
置信度由 0.91 / 0.88 / 0.62 降权为 **0.77 / 0.75 / 0.53**，全部 `needsHumanReview = true`。

## 六、统一隐患口径：唯一判定入口

新增 `taxonomy.isRiskCategory(code)` / `isPositiveCategory(code)` 作为**唯一判定入口**。

- **背景**：此前各处分别手写 `!== 'SAFE_PRACTICE'`，口径不一，
  于是出现 AI 总结说"7 项隐患"、巡检记录表却列出 8 行——
  把"灭火器已配置（正向记录）"也算成了一条隐患。
- **现在**：看板、视频列表、视频详情、分析总结、导出文书**全部调用同一函数**，数字必须一致。
- 已验证：`vid-002` 为 **7 项隐患 + 2 项正向记录 = 9 条打标**；
  看板隐患总数 **11 = 各视频隐患数之和**。

## 七、如何接入真实视觉模型

**只改 `server/lib/vision.mjs` 一个文件**，下游的分段、判定、证据打包、报告、复核闭环无需改动。

### 需要替换的两个函数

```js
// 1) 粗筛：登记候选，不做定性
export function detectCandidates(duration, segments, library, opts) {
  // → 抽帧（每个事件段 1-2 帧/秒）
  // → 调用小模型/文本提示做二分类，只回答"这里有没有 <检查项> 的迹象"
  // → 返回 { candidates, provenance }
}

// 2) 复核：多帧一致性 + 局部裁剪放大
//    在 app.mjs 的 buildFinding 中，把 confidence / stage 的计算
//    换成：关键帧裁剪放大 → VLM 结构化输出 → 多帧投票
```

### 接入要点（踩坑顺序建议）

1. **必须做局部裁剪放大**。本素材只有 960×544 且为第一视角平视，
   直接把整帧喂给模型，安全帽、安全带这类细粒度特征基本判不出来。
2. **多帧一致性投票**。单帧下结论误报极高（反光、遮挡、相似物体），
   至少要"区间首 / 中 / 尾"三帧一致才升为 confirm。
3. **要求模型输出反证**。提示词里明确要求回答"什么情况下这可能不是问题"，
   这一字段直接决定一线愿不愿意用。
4. **模型只输出候选与证据，等级与条款由规则层给**。让模型直接写"重大隐患、违反第 X 条"是不可接受的。
5. **保留 `DEMO_LIBRARY` 作为回归测试标注集**，用于计算召回率与误报率。

### 压力指标（建议验收口径）

| 指标 | 目标 | 说明 |
|---|---|---|
| 高危项召回率 | ≥ 90% | **首要指标**，漏一个重大隐患的代价远大于十条误报 |
| 误报率 | ≤ 20% | 每条误报等于现场白跑一趟，超过一线就会绕过系统 |
| 人工看片时间下降 | ≥ 80% | |
| 高危项自动确认率 | 参考值 | 过高反而危险，说明人工没在看 |

## 十、演示路径建议（5 分钟走完）

1. **总览看板** — 看态势、看趋势、看重复隐患预警
2. **告警复核** — 点一条"移动式操作平台上方有人作业"（置信度 62%），
   看视频自动跳到 00:50 播放、点证据帧放大、读反证与盲区，然后点"确认隐患"
3. **智能检索** — 输入"帮我找临边堆放材料的片段"，看解析结果与 3 秒片段
4. **视频智能分析** — 点"开始智能分析"，看流水线五个阶段跑完，
   读问题总结、展开同类聚类、点"到复核台核对"
5. **硬件管理** — 打开"巡检机器狗-01"，触发实时画面、跑一次 OTA、看告警
6. **录像与告警** — 打开真实素材回放，在时间轴上点色块跳到对应告警
7. **报告文书导出** — 回到**告警复核**页，点视频卡片右上角的**整改单**，下载并打开文书，
   核对每一条隐患的规范依据、AI 判定依据、证据帧与原始视频时间码

## 十一、当前版本的已知限制

- 视觉识别为规则化适配器，**精度指标待接真实模型后重新评估**
- 数据存于内存 + `runs/` 目录，**重启后复核状态与新增任务会重置**（生产需接数据库）
- 所有用户操作使用固定演示账号，未接入登录与权限体系
- 仅挂载了一段真实媒体，多设备/多来源的并发分析未做压力验证
- 报告导出**已实现**（隐患整改通知单 / 安全巡检记录表 / 隐患明细 Excel，HTML 可打印为 PDF），
  但尚未支持直接生成 `.docx` 与 PDF 二进制
- 实时流为演示替代方案，未接入真实流媒体协议
